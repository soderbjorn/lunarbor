# Lunicle boards

Feature spec moved out of `CLAUDE.md` to keep it small. Keep it current when you change the feature.

## Lunicle boards

Lunarbor talks to one or more Lunicle instances (epic LBR-25). LBR-26 is the base: named connections and a typed client. LBR-27 adds the **board node**: a bullet that shows a Lunicle project's board under itself, live; LBR-28 walks it with the keyboard; LBR-29 edits titles and files new issues from it; LBR-30 changes status, priority and assignee from the issue's line; LBR-31 edits the description and adds comments; issues are dragged by their dots to reorder them, change priority or move columns.

- **Connections** (App settings → **Lunicle**, Electron only — the browser demo has no Lunicle at all; `web/.../main/LunicleSettings.kt`): a summary and a "Lunicle connections…" dialog, Agent access's pattern. One card per connection: **name** (the slug in `{{lunicle: <name>/<KEY>}}`: letters, digits, `-`, `_`, unique ignoring case), **base URL** (`https:`; `http:` only for `localhost` / `127.0.0.1`), **personal access token** (`lnl_pat_…`, shown masked to Lunicle's own display prefix; Replace… types a new one, Show reveals what is typed), **Test** (`GET /api/v1/me`: whose token, read-only or read-write, or the error; shown only with a saved token and not while a new one is typed; saving a token runs it at once) and Delete… (confirmed in the card). "Add connection" adds a card with a free name and `https://issues.lunicle.dev`. A hint says tokens are made in Lunicle → Settings → You → API access; a read-only token gives read-only boards.
- **Storage** (`electron-main/.../LunicleHost.kt`): the main process's own `lunarbor-lunicle.json` beside `lunarbor-mcp.json`, mode 0600, `formatVersion: 1`. The renderer never sees a token once entered: `lunarbor:getLunicle` / `addLunicleConnection` / `updateLunicleConnection` / `removeLunicleConnection` answer `{ error, connections }` with `{ id, name, baseUrl, hasToken, tokenHint }`. Name, URL and token are validated there (`lunicleNameError`, `normalizeLunicleBaseUrl`, `lunicleTokenError`; `LunicleHostTest`).
- **Why the main process relays**: Lunicle sends no CORS headers, so the renderer can never `fetch` it — and the token stays out of the renderer. `lunarbor:lunicleRequest({ connectionId, method, path, query, body })` refuses any path outside `/api/v1/` (`isAllowedLuniclePath`: no `..`, encoded or not, no query or fragment in the path), adds `Authorization: Bearer <token>` (and `X-Lunicle-Origin` on writes), times out (connect 8 s, request 20 s), never follows redirects, and answers `{ status, json }` or `{ transportError }`. One `LunicleRemote` per connection holds its token, base URL, request helper and change stream.
- **Client** (commonMain `lunicle/`): `LunicleApi` (the request port, like `NewsFetcher`) and `LunicleConnectionStore`, implemented in `:web` by `ElectronLunicleBridge` (`main/LunicleBridge.kt`); `LunicleClient` — `me`, `projects`, `board`, `issue`, `createIssue`, `updateIssue`, `moveIssue`, `addComment`, each a `LunicleResult` (never thrown); `LunicleRequests` builds them by Lunicle's REST rules (ids in paths only; statuses, priorities, resolutions, assignees **by name** under snake_case names; an unknown argument is a 400, so only set fields are sent, and on an update `LunicleField.Omit` ≠ `Set(null)` — `assignee: null` unassigns); `LunicleModels` parses leniently by hand over `JsonElement` (unknown keys ignored, malformed list entries skipped; `board.assignableUsers` is `null` when absent), errors are `{error, message}` → `LunicleError.Http` (404 also means "not visible", 403 `insufficient_scope` a read-only token, 600 requests a minute per token). Tested in `LunicleModelsTest`, `LunicleClientTest`, `LunicleServiceTest`.
- **`LunicleService`** (app-scoped, `JsAppGraph.lunicleService`, `@Provides @SingleIn(AppScope::class)`; `null` in the demo, so a `{{lunicle: …}}` bullet stays plain text there): the connections flow, add / update / remove (dropping that connection's caches), `testConnection`, and `resolveProject(connection?, KEY)` — the connection by name ignoring case (no name: the only connection, if exactly one), the project by `keyPrefix` ignoring case from `projects()`, cached per connection and refetched once for an unknown key. Handed to `AppShell` by `Main.kt`.
- **Board nodes** (LBR-27, proposal 2a "Properties as tags"; `data/LunicleNode.kt`, modelled on `SearchNode.kt`): a bullet whose text holds `{{lunicle: <connection>/<KEY>}}` (`Lunicle board {{lunicle: work/FRA}}`; the connection part may be left out when exactly one connection exists; `KEY` is the project's key prefix, which survives a rename). The reference is no part of the title: `FolderName.plainTextOf` / `nameTextOf`, breadcrumbs, `pageNodeTitle`, 3D titles and the text index strip it (`LunicleNode.stripQueries`, both node queries at once), and Toggle done leaves it outside the `~~` (`DoneState.coreRange`). Tokenized as one `StyledRun.isLunicleQuery` run: a chip on the caret's row, a small board icon elsewhere (`.lunarbor-md-lunicle`, like a search query's magnifier). **Electron only**: `DocumentRegistry.lunicleBoards` is `null` in the demo (and in tests that pass none), `State.lunicleEnabled` is then `false`, and the bullet is plain text (no chip, no board, an ordinary zoom). A malformed reference shows "Write it as {{lunicle: <connection>/<KEY>}}." in red.
- **Board cache** (`lunicle/LunicleBoards.kt`, owned by `DocumentRegistry.lunicleBoards`, built in `JsAppGraph.provideLunicleBoards`): one `LunicleBoardState` per `LunicleBoardKey` (connection lower-cased, key upper-cased) in `boardsFlow`, mirrored into `State.lunicleBoards`; shaped like `requestSearchNode` — `PaneBackingViewModel.lunicleBoardOf` calls `request` while painting. Each pane reports what it shows after every paint (`reportShownBoards` → `setInterest(pane, board → unfolded issue ids)`; empty for a pane on no editor, cleared in `release`). **Change stream first** (LNL-224): for every connection with a shown, resolved board the main process holds one SSE stream (`LunicleHost.kt`'s `LunicleStream`, `GET /api/v1/events?projects=…&origin=…`, over `lunarbor:lunicleWatch` / `lunarbor:lunicleEvent`, `LunicleEventSource` in `LunicleApi.kt`); it resumes with `Last-Event-ID`, treats 60 s of silence as dead (Lunicle pings every 25 s) and reconnects after 5 s, 15 s, 60 s, then every 5 min (`lunicleStreamBackoffMs`), telling the renderer `connected` / `disconnected` / `unsupported` (404). Events are coalesced for 250 ms (`COALESCE_MS`) and each burst re-reads the board once; `self` events (our writes carry `X-Lunicle-Origin: <LUNICLE_ORIGIN>`, the stream asks with the same `?origin=`) and `notification.changed` are ignored; `board.changed` re-reads that board, `reset` every board of the connection. **Polling is the fallback**: every 15 s (`POLL_MS`) for shown boards whose connection has no live stream, a board coming back into view after more than that is read at once, and window focus re-reads every shown board (`refreshShown`). Issue details (`GET /issues/{id}`: description, comments) are read only for issues a pane has unfolded — on unfolding, and after a re-read for unfolded issues that changed or that an event named (`LunicleBoardDiff.toRefetch`); stale details of other changed issues are dropped. A re-read that changed something shows a notice for 6 s (`NOTICE_MS`, `LunicleBoardDiff.remoteMessage`: "Linus commented on Lönerapporter" from the event's `actor` or a new comment's author, "Lönerapporter moved to Done", "… was added / removed", "3 issues changed"). An error (no such connection, unknown key, 401, offline) keeps the last good board, drawn dimmed. A changed connection list re-resolves boards whose connection changed or that failed. Never written anywhere: not into `Document.lines`, the vault, the text or link index, or anything MCP agents see (they read the bullet's text only); 3D previews show the bullet only.
- **The look** (`web/.../main/LunicleBoardView.kt`, painted by `OutlinePaintLoop` like `buildSearchNodeResults`; rules in `lunicle/LunicleBoardModel.kt`, `LunicleBoardLayout`): the node line has its title, the chip or icon, then the **sync indicator** — a dot and text: "Live" (green, stream connected), "Synced just now" / "Synced 12s ago" (green, kept current by a 5 s timer without repainting), "Saving to Lunicle…" (amber, while a write is under way), "Synced just now" right after one, the remote notice (accent), or the error in red ("Check the token in App settings → Lunicle." for a 401). Under it, unless folded, one `contenteditable="false"` box (no `data-row`, none of the editor's text classes): a row per **column** in board order with its count, columns that need a resolution last and folded by default; a row per **issue** sorted by priority (the board's order within one) — folded: the title, a `#<priority>` pill when it is the highest priority, "N comments" dimmed (only once its details are known: the board call has no comment counts); unfolded: `#<status> #<priority> @<assignee>` pills (`@nobody` unassigned) and the key dimmed, which opens the issue in the browser (`<baseUrl>/?issue=<KEY>`, `https:` only, `MainViewModel.openExternalUrl` → `lunarbor:openExternalUrl`); under an unfolded issue its description (Markdown as read-only lines), one row per comment (text, then dimmed `author · when`) and an inactive "Comment…" row. Pills use the theme's accent, not `tagHue` (they are not tags). Rows look like outline rows (30 px a level, a dot, guide lines, the hover −/+ and a ring round a folded dot); their folds are pane state — `State.lunicleColumnFolds` (`<conn>/<KEY>/<status>` → folded) and `State.lunicleOpenIssues` (`<conn>/<KEY>#<id>`), `toggleLunicleColumn` / `toggleLunicleIssue`; the node itself folds like a search node (`State.collapsedIds`). Zoomed into, the board heads the page, the indicator sits in the page title, and the page is read-only (`ZoomInfo.isBoardNode`, no placeholder child).
- **Keys** (LBR-28; `web/.../main/LunicleBoardCursor.kt`, view state beside `SearchNodeHitCursor`; the rows from commonMain `main/LunicleBoardRows.kt`, tested in `LunicleBoardRowsTest`): **↑ / ↓** from the node's last text line go onto the board's first row, and from the first line of the row below the board onto its last; inside, row by row in `LunicleBoardRows.of`'s order — column name, its issues unless folded, under an unfolded issue its description (the "Loading…" row until read), comments and "Comment…", drafts and issues being filed, and each unfolded column's "New issue" line (LBR-29). Past either end the caret goes back into the document (`Step.LeaveUp` / `LeaveDown`); on the node's zoomed page Down / Up start at the board's top / bottom and the ends hold. **⌘↑ / ⌘↓** (the chords of `setCaretItemFolded`) fold / unfold the column or issue under the cursor (`PaneBackingViewModel.foldLunicleRow`); on a row under an issue ⌘↑ folds the issue and the cursor lands on its title. On the node's own line ⌘↑ / ⌘↓ fold the node itself (`setCaretItemFolded` counts a board node as a parent). **Escape** or a click in the editor leaves onto the node's line. On a row that is not a text field every other key does nothing and is swallowed — typing, Tab, Backspace and editing chords (cut, paste, undo, inline styles) — so the node's line, where the editor's caret is hidden (`.lunarbor-board-cursor-active`), is never edited unseen; other chords (palette, navigation) go on. Fields (titles, drafts, "New issue", a description's lines, "Comment…") take a real caret (see Editing and Details); the others (column names, comments, "Loading…", titles that cannot be edited) a focus tint, as in the prototype. The cursor is keyed by the node's `LineId` and a `LunicleRowRef` (`key`: kind plus issue id, a column by status, a comment by id — never an index) and found again after every repaint (`LunicleBoardRows.relocate`: the same row wherever it moved; a gone comment → its issue, a gone issue → its column, a gone column → the cursor leaves), so a poll that adds issues above never moves it. The painted box carries `data-lunicle-board-row`, each row `data-lunicle-key`.
- **Editing** (LBR-29; rules in commonMain `main/LunicleBoardEditing.kt`, intents on `PaneBackingViewModel`, the field in `LunicleBoardCursor`; tested in `LunicleBoardEditingTest`): on an editable issue's title, a draft or a column's "New issue" line the cursor puts a real `<input>` (`.lunarbor-lunicle-field`) in place of the text — typing, ←/→, selection, copy / paste and ⌘Z within the field are the browser's; the editor's input, clipboard and selection handlers ignore events from it (`MainScreen.fromBoardField`). The same element is put back after every repaint with its text and selection (`saveField` / `mountField`), so neither a poll nor a remote change to that issue overwrites what is typed; a press on a title / draft / "New issue" text starts editing there (`LUNICLE_PRESS_EVENT` → `LunicleBoardCursor.press`). **Titles**: committed when the caret leaves the row (arrows, Escape, a click elsewhere, the field losing the focus to the app, the pane navigating) or on Enter — `leaveLunicleRow` → `LunicleBoards.renameIssue` (`PATCH /issues/{id}` `{title}`) only when the trimmed text changed and is not empty (an empty title comes back as it was, `LunicleBoardEditing.committedTitle`). **Optimistic**: the board shows the new title at once (`LunicleBoardState.titleEdits`) and "Saving to Lunicle…" (`writes`), then "Synced just now" (`savedAt`, `SAVED_MS`) and a re-read; a failure takes the title back and shows the error in red on the indicator for 8 s (`alert`, `ALERT_MS`, `writeErrorText`). The issue being edited stays on the board even if a poll no longer lists it (`State.lunicleEditing`). **Drafts** (`LunicleDraft`, `State.lunicleDrafts` — pane state, never saved, dropped when the pane navigates; a poll never touches them): **Enter** on an issue's title (anywhere: it never splits — it commits the title first) starts a draft right below it in the same column and priority; Enter on a draft with a title files it and starts the next below it; Enter on a column's name puts one at the top of the column with the priority of its first issue, unfolding the column; the last row of every unfolded column is a dim **"New issue"** field — Enter or leaving with text files an issue at the end of the column at the project's default priority, and the line stays (`lunicleEnter`). A draft shows the dim note "new issue · created in Lunicle when you leave the line"; leaving it with a title files it (`LunicleBoards.createIssue`: `POST /projects/{id}/issues` with `title`, `status`, `priority`), its row then shows "Saving to Lunicle…" and the key from the answer (`LunicleCreatingIssue`, shared by every pane) until a re-read lists the issue (the cursor follows it via `createdIds`, `LunicleBoardRows.relocate`). **⌫** on an empty draft removes it, caret to the row above (`removeLunicleDraft`); leaving an empty draft removes it too. Placement is by anchor (`LunicleDraftAnchor`: below an issue, below another new issue, top, end; `LunicleBoardEditing.place`); once filed, the issue goes where the board's own order puts it (Lunicle sorts a priority's issues by last touch). Draft local ids are negative and app-wide (`LunicleBoards.newLocalId`); row keys `n:<local>` (draft), `p:<local>` (being filed), `e:<status>` ("New issue"). **Own writes are not news**: they carry `X-Lunicle-Origin` (the stream marks their echo `self`), and the issues this app changed are left out of the next read's remote-change notice. **Read-only**: a board's first good read asks `GET /me` once per connection (`LunicleService.isReadOnly`, scope `read`), and a write answered 403 `insufficient_scope` marks the connection's boards read-only too; then, or for an issue with `canEdit: false`, its title is no field (a tint), Enter makes no draft, and there are no "New issue" lines (nor for a project viewer, `LunicleBoardState.canCreate`); a key that would edit says why on the indicator once per board and reason (`LunicleBoards.explain`, `READ_ONLY_TEXT`, `noEditText`, `noCreateText`). **Undo**: board edits are remote writes, never in the pane's undo stack — ⌘Z on a board row does nothing; in a field it undoes typing within the field. Allowed on a board node's read-only page too (it edits the board, not the page).
- **Properties** (LBR-30; rules in commonMain `main/LunicleBoardMenu.kt`, tested in `LunicleBoardMenuTest`; intents `PaneBackingViewModel.openLunicleMenu` / `lunicleMenuOptions` / `pickLunicleOption` / `chooseLunicleResolution`; the popup `web/.../main/LunicleBoardMenuPopup.kt`, its state in `LunicleBoardCursor`): **`#`** on an issue's title row — never typed into the title — opens a menu under the line headed `#<query>` with sections **Status** (every column in the board's order, closed ones included) and **Priority**; **`@`** one section, **Assignee**: `@nobody` plus `board.assignableUsers` (LNL-223; same-name users listed twice, as Lunicle sends them). Absent, a token that may file issues is on an older Lunicle: the distinct assignees already on the board stand in (`LunicleBoardMenu.assignees`); absent for a viewer: no `@` menu. Options read like pills (`#in-progress`, `@linus`) with ✓ on the current value. Typing narrows (substring, case-insensitive, against the name and its pill text; "No match" when empty), ↑ / ↓ wrap, Enter or Tab picks, Esc closes, ⌫ on an empty query and a space close (`LunicleBoardMenu.key`). A press on a pill (an unfolded issue's three, a folded one's `#high`; `LUNICLE_PILL_EVENT` → `LunicleBoardCursor.pressPill`) opens a menu for just that field, no sections, the current value highlighted, the caret onto the title; typing there closes it and types. The popup is fixed on `<body>`, the tag autocomplete's look, rows act on mousedown, a mousedown outside closes it. An issue that cannot be edited opens no menu (the indicator says why, once). **Writes** (`LunicleBoards.setProperty`, optimistic through `LunicleBoardState.propertyEdits` / `shown`, reverted with the error — Lunicle's own sentence, e.g. an ambiguous name — like titles): priority and assignee `PATCH /issues/{id}` (assignee by display name, `@nobody` → `assignee: null`), status `POST /issues/{id}/move` `{status}`; picking the current value sends nothing. **Closing statuses**: a status with `requiresResolution` first opens a small popup of the project's resolutions (first highlighted, ↑ / ↓ / Enter, Esc cancels the move); the move carries the pick. **Move and flash** (`LunicleBoardMenu.placeAfterChange`, `State.lunicleFlash`, `FLASH_MS` 1.5 s): the issue shows under its new column at once and flashes there (`is-flash`, a `--t-warn` wash fading out; a repaint resumes it by a negative `animation-delay`), the caret follows; a folded target column unfolds — except a folded closing column (one folded by default), which stays folded while its row flashes, takes the caret and counts one more. Every pick flashes, priority and assignee too.
- **Details** (LBR-31; rules in commonMain `main/LunicleBoardDetails.kt`, tested in `LunicleBoardDetailsTest`; drawn by `LunicleBoardView.appendIssueChildren`, edited through `LunicleBoardCursor`): an unfolded issue's first child row is its **description** — one row holding a bordered box (a block's look) with a line per Markdown line (`LunicleDescription.linesOf` / `textOf`, an exact round trip), each rendered (inline Markdown, list dots, headings, quotes, code in a monospace band, fences dim) except the caret's, which the cursor's field covers raw; empty, "Add a description" dim ("No description" when it cannot be edited). Landing on it (from above its first line, from below its last, a press on a line) starts an edit: the lines become pane state (`State.lunicleDescriptionEdit`, `PaneBackingViewModel.beginLunicleDescription`), so neither a poll nor the change stream overwrites them. Inside (`editLunicleDescription` → `LunicleDescription.apply`): **↑ / ↓** go between lines (on the first / last line they leave, continuing the board cursor), **Enter** adds a line (continuing a `* ` / `- ` / `1.` item, an empty item ends the list), **Backspace** at a line's start and **Delete** at its end join lines, a multi-line **paste** goes in verbatim (the field's `paste` listener; a single line is the field's). Leaving commits (`leaveLunicleRow` → `LunicleBoards.setDescription`: `PATCH /issues/{id}` `{description}`, only when the text differs from the one the edit started from; optimistic via `LunicleBoardState.descriptionEdits`, reverted with the error). **Remote change during an edit**: when the board's description no longer matches the edit's original (`LunicleDescription.changedRemotely`), the indicator says "<title>'s description changed in Lunicle; your edit is kept" (REMOTE, for as long as the edit runs) and leaving sends the user's text — the commit wins. A **large** description (16+ lines, `BlockLayout.FOLD_MIN_ROWS`) shows its first 8 rows, the last fading, with "N more lines" and an expand / collapse control (`State.lunicleOpenDescriptions`, `toggleLunicleDescription`); the caret landing past the preview expands it. **Comments**: one row each, oldest first, the body inline only (lines joined, `LunicleComments.inlineBody`), then dim `author · when` (`LunicleComments.whenText`, clock and time zone as parameters: "just now", "5m", "3h", "1d" / "2d", the weekday within a week, then "4 Oct" / "4 Oct 2025"). A comment that arrived since the pane last saw the issue (`State.lunicleSeenComments`, checked on every board change and on unfolding, `noteLunicleArrivals`) flashes for 4 s (`State.lunicleArrivedComments`, `ARRIVAL_MS`); this app's own posts never do (`LunicleBoardState.ownComments`; writes carry `X-Lunicle-Origin`, so their stream echo is `self`). Descriptions and comments are drawn with Markdown's backslash escapes (`\*` shows `*`, as in Lunicle: `InlineMarkdownTokenizer.tokenize(…, escapes = true)`; off for outline rows, whose text the codec already unescapes). Comments are read-only here: editing and deleting stay in Lunicle (the key opens the issue). **"Comment…"** is the last child row, a field: Enter with text posts (`lunicleEnter` → `LunicleBoards.addComment`: `POST /issues/{id}/comments` `{body}`), the comment showing at once, faded, as the token's owner (`GET /me`'s name, `LunicleService.userName`, else "You") until a read of the issue lists it, and the field empties; on an error the comment goes, the indicator shows it in red, and the text goes back into the input (`State.lunicleCommentDrafts`, merged into an open field by `takeLunicleCommentDraft`, `LunicleComments.mergeDraft`). Text left there unposted stays with the row. **Read-only**: with a read-only token, or Lunicle's `canComment: false` (or `canEdit: false` for the description), the description is not editable (a tint; typing says why once) and "Comment…" is hidden.
- **Drag** (rules in commonMain `main/LunicleBoardDrag.kt`, tested in `LunicleBoardDragTest`; the gesture `web/.../main/LunicleBoardDragGesture.kt`): an editable issue's dot drags the issue, as on Lunicle's board — a press that moves 4 px is a drag, one that does not still folds / unfolds. The row under the pointer decides (`LunicleBoardDrag.dropAt` → `LunicleDrop`): an issue's upper / lower half puts it directly above / below that issue in **its** column and priority (so the boundary between two priorities offers both: below the last `#high` stays high, above the first `#medium` becomes medium; below an unfolded issue is below its subtree); an issue's child rows mean below it; a column's "New issue" line below its last issue; a column's name into that column, keeping the priority, last in its group. A column that requires a resolution (Lunicle groups it by resolution, not priority) only takes "into" — the resolution popup first (`LuniclePick.NeedsResolution`, then `chooseLunicleResolution`'s move) — and a drag inside it does nothing; drafts, the issue itself and a drop where it already is give none. The drop is marked on the row (`is-drop-before` / `-after` / `-into`, the dragged row `is-dragging`; put back on every repaint, `LunicleBoardDragGesture.decorate`); Escape cancels. `PaneBackingViewModel.dropLunicleIssue` → `LunicleBoards.dragIssue`, optimistic (`LunicleBoardState.orderEdits`, `LunicleOrderEdit.applyTo`: the issue next to its anchor in the board's flat list, which the stable priority sort keeps in place): a new column `POST /issues/{id}/move`, then `PUT /issues/{id}/order` (`reorder_issue`: `before_issue_id` / `after_issue_id`, `priority` only when it changed); a Lunicle without that route (404) gets the priority by `PATCH` and the indicator says reordering needs a newer Lunicle; a failure reverts and re-reads. The issue flashes in its new place and the caret follows (`LunicleBoardMenu.placeAfterChange`, as for a property change).
- **Delete** (palette "Delete Lunicle issue <KEY>…", offered while the board cursor is on an editable issue's title or a row under it — `LunicleBoardCursor.selectedIssue`, `PaneBackingViewModel.lunicleIssueToDelete`): a destructive confirmation, then `deleteLunicleIssue` → `LunicleBoards.deleteIssue` (`DELETE /issues/{id}`, comments with it; permanent, not optimistic — the issue leaves the board on Lunicle's answer, an error such as no right to delete shows in red on the indicator); the cursor relocates to the column.
- **Insert** (palette "Insert Lunicle board…", Electron only, `AppShell.insertLunicleBoard`): a one-off command palette picks the connection (skipped when exactly one has a token), another the project (`projects()`); `PaneBackingViewModel.insertLunicleBoard` → `TextEditingViewModel.insertLunicleBoard` puts `Lunicle board {{lunicle: <conn>/<KEY>}}` (always the full form) where Insert search node would, the title selected; one undoable edit.
